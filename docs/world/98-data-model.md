# 98 — The data model: every entity's home table

Read this before you write or read a world record, and at place-build step
0. It is the map; the rules are decision 0104 (one home table per entity,
references by id, promises are records, the integrity gate) and
engineering standard 18. Field-by-field schemas live in
`packages/world-schema/schemas/` (one JSON Schema per family, the ones
`families.json` lists) and in each folder's README.

## The rule in one paragraph

Every entity lives in exactly one authored file (its home) under a stable
id with a unique prefix. Every other file refers to it by that id and
never copies its fields. Files under `apps/world-studio/public/` and
`tooling/*/output/` are DERIVED: a pipeline step regenerates them from the
homes and nobody edits them by hand. When a derived file is wrong, fix its
home and re-run the step. `npm test` proves every id reference resolves
(`packages/world-schema/integrity.py`) and that the derived files are
current (for example `test_export_places.py`).

## Record = built

The place record, the map popup and the built place must agree. The
popup reads `places.json`, which `export_places` derives from the
catalogue, so the record is the only thing to edit. When the build
changes the world, the builder edits the record and the quests that read
it in the same change (0104 decision 6). The record must also agree with
itself, the world around it (routes, neighbours, water), every quest that
uses it and lore: place-build step 5b runs the record-coherence protocol
(0117; five readers over the packet from `worldgen.record_coherence`, one
change set). Three gates hold the measured part: `record.consistency`
(the counted buildings against the record's magnitude band in
`breadth-bars.json`), `record.coherence` (every place and route the
prose and its quests name resolves and is related to the place, a
"between A and B" has its route, a quest's premised feature exists) and
`promises` (every ledger row filled or confirmed).
