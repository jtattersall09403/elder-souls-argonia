# 0104 — The world is one normalised record set: every entity has one home table, references are ids only, promises are records that placed interactables fulfil, and a gate proves every reference resolves

**Date:** 2026-09-27. **Owner steer:** "I'm a data scientist, I'm
thinking about our game as data ... one big sensible connected data
structure ... code first and data first ... easy adding, updating,
deleting (like 3NF)." **Evidence:** the data-model sweep of this date
(`tooling/.reports/16k/walk2/data-model.md`): the Claywater ferry poler
appears in five records under three ids; three socket vocabularies
(catalogue buckets, `interior.anchorSockets`, the 0103 placed sockets);
doors in five places; 149 `quest.provision.*` ids with no defining
table and no link from a placed socket to the promise it fills; the
`station` prefix meaning three things; catalogue and quest writers
rewriting whole files with no lock.

## What the industry does, and what we take from it

Bethesda's own games are the reference: an `.esm` is a record database,
every record keyed by a stable FormID, references between records by
FormID only, and the game engine reads the compiled database. Most
data-driven studios author in a relational store or spreadsheets and
export to JSON or binary for the runtime; graph databases are rare in
games and add nothing we need. A relational database inside the repo
would cost us git diffs, deterministic compilers and agent-friendly
plain files. **We keep JSON records in git as the authoring database**,
and we adopt the relational discipline on top of them: one home table
per entity kind, stable ids as primary keys, references by id, no
duplicated facts, a schema per table, and referential integrity checked
by a test. That is third normal form applied to files.

## Decisions

1. **One home table per entity kind.** Every entity lives in exactly one
   record family (its home), keyed by a stable id registered in
   `tooling/repo-standards/id-registry.json` (standard 2 now covers
   sockets, doors, promises, travel services, blueprints and layouts).
   Derived files (a blueprint export, a compiled bundle, a studio
   manifest) are build outputs of a pipeline stage and are never edited;
   they carry the hash of the authored record they were derived from.
   The authored pose of a placed thing is its layout op; the blueprint
   and the compiled record are stages, not second copies.
2. **References are ids, never copies.** A record that needs a fact
   from another record refers to it by id; a copied field is a defect
   the integrity gate reports. Prefixes are unique per family:
   `place.`, `parcel.`, `door.`, `socket.`, `promise.`, `travel.`,
   `npc.` (the NPC registry only), `quest.`, `route.`, `kit:` assets.
   The catalogue's `sockets.station` bucket is renamed `post` (an NPC's
   work post) so `station` means a travel stop only; layout socket ids
   carry the place segment (`socket.<place-slug>.<slug>`) like every
   other placed id.
3. **Promises are records.** A place's promises (its catalogue
   `services`, `occupants`, `sockets.*` buckets, `questHooks.provisions`,
   the quest provisions of quests 20 and the travel-service operator
   slots) are compiled into one promise ledger record per place,
   `world/sources/placement/promises/<place-id>.json` (`schemaVersion`
   1), one row per promise with a stable id `promise.<place-slug>.<slug>`,
   its kind, its source record and field, and its text. The ledger is
   generated by `blueprint_promises` from the source records (never
   hand-written) and committed, so a diff shows a promise changing.
4. **A placed interactable fulfils promises.** `sockets[]` (0103) is the
   home table of placed interactables, exterior and interior alike; a
   socket carries `fills: [promise ids]`. The kinds are `npc`, `idle`,
   `item`, `container`, `station` (a crafting or work fixture: forge,
   tanning rack, cooking spit, fish rack, loom; `stationClass` from the
   vocabulary), `sign` (`pointsTo[]` of route and place ids, one per arm),
   `encounter`, `fauna`, `ambience`, `marker`. Doors stay their own
   family (a transition, not a socket) with `doorType` `load` (a cell
   transition) or `swing` (opens in place by animation, no cell) and a
   `fills` slot for the promises a door meets (a D0 safe interior).
   Every socket, door, sign and station carries `owner` and `valueTier`
   slots (build-out hook, decision 0041), empty until Phase 13.
5. **The promise gate is the builder's checklist.** `compile_settlement`
   fails a place whose ledger has a promise no socket, door or parcel
   `fills`, unless the promise row carries an `unfilled` block with one
   of the four 0102 gap reasons. The design brief's § Promises table is
   the ledger with a fulfilment column; the builder starts from it,
   works through it and ends on it. The walk packet prints the count
   (filled, unfilled with reason) and nothing else about promises.
6. **Two-way.** A promise the world cannot keep (an asset that exists
   nowhere after a completed search, a quest asking for an item class we
   cannot show, a service the ground forbids) is corrected at its source
   record by the place builder in the same slice: the quest provision or
   catalogue field is edited, the prose reviewed with `text-review`, the
   ledger regenerated, and the change recorded in the brief's § Record
   corrections with the reason. The builder holds this authority; it
   never leaves a promise both unfilled and unedited.
7. **Referential integrity is a test.** `npm test` runs a gate that
   loads every record family through the schema registry and checks
   every id reference resolves to a record of the expected family, every
   promise is filled or excused, and no two families define the same id.
   Shown failing first on the ferry-poler duplication.
8. **Schemas live in one package.** `packages/world-schema` (which
   world 80 already claims) holds one JSON Schema per record family,
   versioned by `schemaVersion`, and the TypeScript types the runtime
   uses are generated from them; Python readers validate against the
   same files. A new family without a schema fails the gate.
9. **Writers are atomic and locked.** Every whole-file writer
   (`catalogue.dump_json`, `quests.dump_json`, plot remedies, travel
   services, patches, crossings) writes to a temp file and renames under
   a `flock`, the way `kit_lock.py` does, so concurrent lanes never
   clobber each other.

## What changes now (slice 1c) and what is queued

Now: decisions 3–7 and 9, the vocabulary kinds of decision 4, the
`doorType` field, the `post` rename and the layout socket id form, the
`world-schema` package with schemas for the families the place loop
writes (promises, sockets, doors, layout, blueprint, travel services,
socket vocabulary). Queued with owners: schemas for the remaining
families and the generated TypeScript types (the 16k exit, before Phase
13 reads sockets); the `interior.anchorSockets` vocabulary folded into
the socket vocabulary when Phase 12 opens.

## Consequences

- A promise is visible as data from the day it is made to the day it is
  filled, and a later phase (13 loot, 10b people, 12b sound) reads the
  socket table and fills it, adding no vocabulary.
- "Did the builder cover everything the record promised?" is a compile
  gate, not an owner question.
- The runtime's `InteractionCandidate` is built from the socket and door
  tables; nothing else describes an interactable.
