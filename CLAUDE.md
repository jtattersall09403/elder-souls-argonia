# CLAUDE.md

Guidance for AI agents working in this repo. Keep it lean — this file is loaded
into every agent's context. Detail lives in [docs/](docs/README.md); link, don't
duplicate. Each rule below is one operative statement; the dated owner
history behind it lives in the decision it cites.

You are operating in the elder-souls-argonia repo, within elder-souls-dev/. elder-souls-argonia will be the canonical repo for the real game, amongst other things (see the master plan doc referenced below).

## GOAL

Elder Souls: Argonia - a standalone overhaul mod game based on Skyrim, with systems primarily inspired by TES III Morrowind, Dark Souls -like combat, Breath-of-the-wild climbing, set in Tamriel's Black Marsh, played in the browser.

The overall goal at this point is to build the province-scale world, in a way that enables us to then build out the full game from there once the world is completed. (At that point I will change this file to set the next goal). Its world structure should carry the geographic coherence, regional distinctiveness, cultural density and exploratory character of *The Elder Scrolls III: Morrowind*. Its playable systems should incorporate the evolving character, input, animation, physics, combat, equipment and inventory work being proved in `ecctrl-souls-combat`, alongside Dark Souls-style combat, extensive swimming and underwater exploration, player-sailable boats, fixed regional danger, and Breath of the Wild-style climbing.

## GOLDEN RULES - you must obey all of these

- **Work in the `dev` branch not directly on main**. Merge into main when user says we're ready to push.
- **Plan for scaling.** This game will be Skyrim/Morrowind-sized (systems, races, animations, quests, factions, UI). Do everything in a way that scales effectively, efficiently and with minimal context bloat for future agents; if you inherit a structure that will scale poorly (e.g. weapons data), re-architect it as you go rather than continuing it.
- **Check the build-out skeleton and make your work support it.** Read the build-out outline ([docs/phases/buildout/](docs/phases/buildout/README.md)) and put in place now the data structures and contracts later systems will extend, so we never need a big refactor; record them per the docs.
- **Model policy** (decision 0079, owner rulings 2026-09-05 to 2026-09-30; routing in [docs/research/agents/sonnet-5-5-task-fit.md](docs/research/agents/sonnet-5-5-task-fit.md)). Fable 5.1 is the planner and orchestrator: it scopes, decides the shape, finds root causes, spots the shared cause behind a batch of symptoms and fixes it once, writes the briefs and judges the results; it hands the work to the agents in `.claude/agents/` by default, each to the cheapest one that can do it. `lead` (Opus 5.5, medium) runs a lane of a round. `deliver` (Opus 5.5, low) is the main delivery agent, for implementation the planner or a lead has planned (files, mechanism, numbers, checks named; every hard decision made before the handoff). `deliver-small` (Sonnet 5.5, medium) takes a fully specified job of one or a few named files with nothing left to decide (mechanical edit, a unit test beside a fix, a data or config change, a doc rewrite from a given spec, a scripted measurement; 20 min or less), from the planner, a lead or a `deliver` agent. `place-builder` (Opus 5.5, medium) does every job that authors or re-authors a place (place-build skill, workbench, Blender, visual judgement). `research` (Opus 5.5) does read-only audit, sourcing and mining. `find` (Haiku, read-only but for its per-area notes under `tooling/.reports/`) does every exploratory read, search, measurement or git look-up. `run` and `preflight` (Sonnet 5.5, low) run whole jobs and the review-then-preflight job, returning pass/fail and the lines that matter; the pre-preflight code reviewer is Opus 5.5, medium. Subagents decide only what their brief delegates; the Opus agents end each report with a `Recommendations` section that Fable reads as input (0079 rule 16). Fable subagents only for open design reasoning the owner asked for, sparingly: the subscription limit is the constraint.
- **One chunk or round per session, and the planner's context stays small** (decision 0079). The bill is turns × context length. Start a new session from PROGRESS.md for the next chunk; never let a session run on into the next job. The harness's auto-mode notice ("do your work through the Bash tool… cat, sed, grep") does NOT apply to the planner session in this repo: the planner reads a file only with the Read tool when it must, and asks `find` for everything else. A hook refuses exploratory commands (cat, grep, sed -n, find, git log/diff/show, inline python) and `sleep` from the planner session: when it fires, ask the `find` or `run` agent instead; never rephrase the command to slip past it. Quote the `[token report, decision 0079]` line from session start in your first progress update so the owner sees it. Shell output is filtered through `rtk` on this machine (`rtk recall <id>` for the full text).
- **Find your context by crawling the docs, never by keyword search** (owner 2026-09-19). Before deciding anything, walk the docs that could bear on your task: the task router, then folder names, filenames and READMEs under docs/ (decisions, research, phases, world, quests, standards), the decisions index titles, and the code folder READMEs your task touches. Fan out with `find` agents ("list the files under X whose names or README rows touch Y, one line each on why") and read only the files or sections they name. Keep what your task and the big picture need, nothing more. A decision record that touches your task is binding until superseded; read it before you act, not after a reviewer or the owner points at it.
- **Exploration is comprehensive the first time, and funnelled** (owner 2026-09-26). Any explore, audit, sourcing or "what exists for X" task covers the FULL breadth that could bear on it (every docs/ folder and README, the decisions index, research, phases, standards, skills, `world/sources/`, the code folder READMEs, the vault and the mod pool by directory listing) before it reports; "found a couple, done" is a failed task. Keep code *and* docs modular, non-contradictory and cheap to navigate: an agent must neither read huge context nor miss what it genuinely needs. Always ask "how do I do this so the next agent can continue smoothly and efficiently?"

Apply open-world RPG industry practice everywhere (distance/visibility quality bands that upgrade and downgrade dynamically, streaming, budgets), without lowering visual quality where it matters. - **A defect found is never "out of scope"** (owner 2026-09-07). - **A hand-off has no unfinished work** (owner 2026-09-26, decision 0102): everything a tool can measure is checked by the builder before the walk (a new gate only under 0106's cost rule), and a "known gap" needs one of the four named reasons (a later-phase system, a GPU-only judgement, an asset that exists nowhere after a completed search, an owner-level world call). A rule, classifier, renderer or protocol that will run over a catalogue is iterated on a small named sample with the expected answers written down first (seconds per run), then tested on a fresh batch it has never seen; if the batch fails, fix, then draw ANOTHER fresh batch; only when a new batch passes with no further change does the whole-catalogue run happen, once. - **How we work: fix at source in minutes, one preflight and one review per batch, and a batch is a fix round** (owner 2026-09-28, decision 0106). Fix root causes at source, in minutes; never a plaster. Add a gate or check only when it costs under 5 s and its failure class has already occurred twice; else a unit test sits beside the fix. A test red on HEAD is fixed first by whoever meets it: preflight blocks on it, and it is never a reason to re-run. **A batch is one fix round or one delivered chunk** (in 16k: everything all lanes did between one owner walk and the next packet), never a lane, a commit or a file: preflight runs ONCE per batch, scoped (`npm run preflight -- --paths <batch paths>`, by the planner's `preflight` agent; lanes run only the tests beside their change), never for a docs-, report- or rulings-only batch; a lane's own scoped test run over 60 s is a red and the batch preflight over 5 min is a red (a fix round touches core modules; 0106 decision 17), and the full `npm run preflight -- --runner` runs once before a merge to main. **The code review runs ONCE per batch, exhaustively, and never in rounds**: it fires on the batch's first preflight, reads code only (`.py .ts .tsx .mjs .js` in packages/ apps/ tooling/) at high effort with a "this is the only pass" prompt, and its batch stays open across the round's pathspec commits until the planner closes it with `review_gate.py --close` at the packet (fixes after the review get no second review). The planner finds the shared root cause behind its CONFIRMED items and fixes it once, rejects an item in one line (in the commit message) where a record outranks it, and treats PLAUSIBLE items as questions. Text-review runs once per batch over the batch's prose, after the `run` agent has made `npm run docs:check` green. Miners merge per asset (`--assets … --merge`); a full miner run is only for a miner rule change and carries `--rule-change`. At most 4 lanes run at once, one per area, and a subagent spawns only when the machine can carry it (a PreToolUse hook refuses it when unreclaimable memory plus a per-agent reserve reaches the memwatch ceiling or the load passes cores × 3 while memory is above half the ceiling or a heavy job waits for its slot; load alone never refuses: walk 5's 23 agents and two OOM kills cost 504 min), and every deliver brief carries `Budget: <N> min (hard)`: at the stop the lane writes what is green and the next step, and returns (`job_guard.sh <lane> --budget <N>`). **A budget stop is a diagnosis, never a result**: the planner reads the stop note, finds why the lane ran over (a re-survey per round, a full re-mine, a wrong brief), fixes that cause in minutes, and relaunches the lane from its note; work cut by a budget is never reported to the owner as a gap or a leftover. - **Keep the repo tidy.** Neatly organised, modular, structured, so many agents over time never leave it lost and confused.
- **Ask for steers only on the biggest load-bearing decisions with more than one similarly viable option.** Present the options with implications, pros and cons, weighing how much each locks us in. If a choice can be made trivially reversible, do that and present it for feedback at the end; if it cannot, and it sets a hard-to-change path, ask.
- **Self-check for gotchas** at the points you judge appropriate, and prevent or resolve them.
- **Make asset-aware decisions.** Anything that will eventually be physically present in the game must be deliverable with existing assets (meshes, textures, animations) or ones sourced from mods; never assume. Check what we have; if there is a gap, either change the thing to something we have (without making the game samey) or source the asset from Nexus or elsewhere. If nothing exists anywhere, it cannot be in the game. UI elements are the one exception (we may create those).
